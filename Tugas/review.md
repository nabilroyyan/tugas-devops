| 5 | Masalahnya bukan sekadar scanner, melainkan security gate yang tidak memiliki kriteria dan proses triase yang jelas. Tetapkan threshold transparan, prioritaskan temuan berdasarkan risiko, dan sediakan waiver yang terdokumentasi, memiliki pemilik, serta kedaluwarsa. |
| 6 | Evidence yang dapat diproses dan diaudit—misalnya laporan SARIF, SBOM, attestations, hasil evaluasi kebijakan, dan log deployment—yang ditautkan ke commit, pipeline, serta digest artefak. Screenshot saja tidak cukup sebagai sumber bukti utama. |

| 10 | Jangan mengubah permission socket menjadi `666`; itu memberi akses luas ke Docker daemon yang dapat setara dengan akses root. Periksa status daemon dan gunakan akses yang dibatasi, misalnya keanggotaan grup Docker dengan memahami risikonya, atau rootless Docker. |
| 11 | Container mengisolasi proses menggunakan kernel host yang sama, sedangkan VM menjalankan guest OS dan kernel sendiri. Container umumnya lebih ringan dan cepat dimulai, sementara VM menyediakan batas isolasi yang lebih kuat. |
| 12 | PID namespace hanya mengisolasi tampilan proses; **tidak membatasi pemakaian memori**. Gunakan limit cgroup seperti `--memory`, ukur penggunaan resource, dan periksa metrik serta event OOM. |
| 13 | `Exited (137)` paling mungkin menunjukkan proses dihentikan karena kehabisan memori/OOM, sehingga kebijakan `on-failure` mencoba menjalankannya kembali. Periksa `docker inspect` (termasuk status OOM), log, penggunaan memori, dan apakah limit 64 MB cukup untuk workload. |
| 14 | Tag `latest` dapat berpindah menunjuk image berbeda, sehingga versi yang terpasang tidak pasti dan build/deployment sulit direproduksi. Gunakan tag versi spesifik; untuk mengikat ke konten tertentu, pin digest dan perbarui secara terencana. |
| 15 | **`runc`** adalah low-level runtime yang langsung membuat proses container sesuai OCI Runtime Specification. |
| 16 | Container berjalan di latar depan dengan proses utama yang segera selesai dengan exit code `0`; Docker lalu menandainya `Exited (0)`. `docker ps` hanya menampilkan container yang sedang berjalan, sedangkan `docker ps -a` juga menampilkan yang sudah berhenti. |
| 17 | `EXPOSE 80` hanya mendokumentasikan port container; itu tidak memublikasikan port ke host. Jalankan dengan pemetaan, misalnya `docker run -d --name pens-app -p 9090:80 pens-web:1.0`. |
| 18 | Pengguna yang ditambahkan ke grup `docker` dapat mengendalikan daemon Docker, yang pada praktiknya dapat memberikan kemampuan setara root pada host. Berikan akses hanya kepada pihak yang dipercaya; pertimbangkan rootless Docker bila sesuai. |
| 19 | Salin file dependensi terlebih dahulu, instal dependensi, baru salin kode aplikasi. Contoh: `COPY requirements.txt .` → `RUN pip install -r requirements.txt` → `COPY . .`. Perubahan kode dengan demikian tidak selalu membatalkan cache instalasi dependensi. |
| 20 | Tambahkan `.env` dan file rahasia ke `.dockerignore`, lalu gunakan BuildKit secret mount untuk kredensial saat mengunduh dependensi privat—bukan `COPY`, `ARG`, atau `ENV` untuk menyimpan token. Rotasi token yang sudah terlanjur masuk image dan jangan mengandalkan rebuild saja untuk menghapus paparan image lama. |
| 21 | `server-a` dan `server-b` berada di network yang berbeda, sehingga `server-a` kemungkinan tidak dapat menyelesaikan nama `server-b` melalui DNS Docker. Hubungkan keduanya ke `lab-net` agar dapat berkomunikasi dan menggunakan discovery nama service/container di network tersebut. |
| 22 | Jangan publikasikan dashboard langsung ke semua interface host. Batasi akses ke interface internal/localhost jika memungkinkan, atau letakkan di belakang reverse proxy dengan autentikasi dan firewall yang membatasi sumber akses; jangan publikasikan port yang tidak diperlukan. |

| 24 | Gunakan **`tmpfs`** untuk file sesi sementara yang sensitif dan tidak perlu bertahan setelah container berhenti atau restart. |
| 25 | `:ro` memasang volume sumber sebagai **read-only** agar backup tidak mengubah data sumber. `--rm` menghapus container backup otomatis setelah prosesnya selesai. |
| 26 | Bind mount menutupi isi direktori pada image dengan isi direktori host. Karena `./html` kosong, file default Nginx tersembunyi; Nginx tidak menemukan halaman yang bisa disajikan dan dapat mengembalikan 403. Isi direktori host atau lepaskan mount tersebut. |
| 27 | `docker compose down -v` menghapus container, network project, **dan named volume** seperti `pg-data`. Data PostgreSQL di volume itu akan hilang; gunakan `docker compose down` tanpa `-v` bila data harus dipertahankan. |
| 28 | `depends_on` dengan kondisi `service_healthy` menunggu healthcheck database berhasil sebelum app dimulai. Ini membantu urutan startup, tetapi tidak menjamin database akan selalu tersedia setelah app berjalan. |
| 29 | Jalankan **`docker compose config`** untuk melihat konfigurasi akhir setelah interpolasi variabel dan penggabungan file Compose. |
| 30 | Pemisahan network membatasi jalur komunikasi: `web` berkomunikasi dengan `app` melalui `frontend`; `app` berkomunikasi dengan `db` melalui `backend`; `db` tidak terhubung ke frontend dan tidak perlu memublikasikan port. |
| 31 | Apache httpd mendukung modul dan konfigurasi seperti virtual host serta `.htaccess`; Nginx umum digunakan untuk reverse proxy dan penyajian file statis. Keduanya memiliki pola konfigurasi yang berbeda, dan pilihan bergantung pada kebutuhan—bukan karena salah satunya selalu lebih baik. |
| 32 | Reverse proxy tidak memiliki seluruh konteks bisnis aplikasi. Validasi input, autentikasi, otorisasi, dan pengelolaan sesi tetap harus diterapkan pada backend. |
| 33 | Perintah itu membuat sertifikat **self-signed** RSA 2048-bit untuk 365 hari dengan subject `CN=localhost` dan `O=PENS Docker Lab`. Opsi `-nodes` membuat private key tanpa enkripsi passphrase; sertifikat ini cocok untuk lab, bukan otomatis dipercaya klien produksi. |
| 34 | Backend menerima path **`/health`**. Slash di akhir `proxy_pass http://flask-app:5000/;` mengganti prefix `/api/` dengan `/`. |

| 39 | Mulai dengan memeriksa status container dan log Nginx serta backend.
